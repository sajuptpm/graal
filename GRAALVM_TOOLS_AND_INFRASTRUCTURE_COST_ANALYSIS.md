# GraalVM Tools & Infrastructure Cost Analysis (Before Workflow Optimization)
## Including Alternative Low-Cost & Native GitHub Solutions for Open-Source Fork Releases

## Executive Summary

This document provides a comprehensive audit of all developer tools, continuous integration (CI) infrastructure, cloud compute instances, specialized testing services, security analyzers, artifact repositories, and external APIs utilized across the **GraalVM** repository (`oracle/graal` and forks) prior to key workflow optimizations (such as removing expensive high-memory larger runners, filtering PR executions on internal forks, and stabilizing gate matrix runs).

In addition, for each component, this document specifies the **Alternative Low-Cost and Native GitHub Solution for Open-Source Release from a Fork**, enabling independent maintainers to build, validate, package, and release GraalVM community distributions on GitHub with **zero or near-zero infrastructure expenditure**.

## Blueprint: Zero-Cost Native GitHub Workflow for Fork Releases

To release GraalVM community binaries from an open-source fork without paying for GitHub larger runners or enterprise infrastructure, implement the following native GitHub Actions workflow:

```yaml
name: Release GraalVM Community Distribution (Fork)

on:
  push:
    tags:
      - 'v*'
  workflow_dispatch:

permissions:
  contents: write

jobs:
  build-release-linux:
    name: Build GraalVM CE Linux x64
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Fork Repository
        uses: actions/checkout@v4

      - name: Expand Virtual Memory (10 GB Swap to prevent OOM)
        run: |
          sudo fallocate -l 10G /swapfile
          sudo chmod 600 /swapfile
          sudo mkswap /swapfile
          sudo swapon /swapfile

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Set up Bootstrap Java
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '21'

      - name: Checkout mx
        uses: actions/checkout@v4
        with:
          repository: graalvm/mx.git
          path: mx

      - name: Build GraalVM CE
        env:
          MX_PATH: ${{ github.workspace }}/mx
        run: |
          ${MX_PATH}/mx --primary-suite-path vm --native-images=native-image --components="Native Image" build
          GRAALVM_HOME=$(${MX_PATH}/mx --primary-suite-path vm graalvm-home)
          ARCHIVE_NAME="graalvm-ce-linux-amd64-${{ github.ref_name }}.tar.gz"
          tar -czf ${ARCHIVE_NAME} -C $(dirname ${GRAALVM_HOME}) $(basename ${GRAALVM_HOME})
          sha256sum ${ARCHIVE_NAME} > ${ARCHIVE_NAME}.sha256

      - name: Publish to GitHub Releases
        uses: softprops/action-gh-release@v2
        with:
          files: |
            graalvm-ce-linux-amd64-*.tar.gz
            graalvm-ce-linux-amd64-*.tar.gz.sha256
          generate_release_notes: true
```

## Deep Dive: What are "Coordinates" in Row 1?

In the Java / Maven / Gradle ecosystem, every dependency is uniquely identified by its **Maven Coordinates** (also called **GAV Coordinates**):
```
<groupId>:<artifactId>:<version>
```
For example:
- `org.slf4j:slf4j-api:2.0.16`
- `com.google.guava:guava:33.3.0-jre`
- `io.netty:netty-codec-http:4.1.100.Final`
- `com.fasterxml.jackson.core:jackson-databind:2.15.2`

### Why does GraalVM CI test 256 coordinates?
1. **Ahead-of-Time (AOT) Reflection Challenge:** GraalVM Native Image compiles Java bytecode directly to native machine code ahead-of-time. Dynamic features like reflection, JNI, serialization, and dynamic proxies require configuration files (called **reachability metadata**) to prevent classes and methods from being pruned during dead-code elimination.
2. **The Reachability Metadata Repository:** Oracle maintains an open-source repository ([`oracle/graalvm-reachability-metadata`](https://github.com/oracle/graalvm-reachability-metadata)) containing pre-computed metadata for hundreds of popular third-party Java libraries.
3. **The Matrix Generation in CI:** In [.github/workflows/reachability-metadata-template.yml](file:///c:/projects/graal/.github/workflows/reachability-metadata-template.yml#L87-L125), the `populate-matrix` step queries the repository for the top 256 most dynamic Java libraries:
   ```bash
   ./gradlew listTopCoordinatesByMetric --metric=dynamic-accesses --limit=256 > coordinates.txt
   ```
4. **Dynamic GitHub Matrix:** The resulting 256 GAV coordinates are converted into a dynamic GitHub Actions JSON matrix:
   ```yaml
   strategy:
     matrix:
       coordinates: ["org.slf4j:slf4j-api:2.0.16", "io.netty:netty-codec-http:4.1.100.Final", ...]
   ```
5. **Parallel Matrix Jobs:** GitHub Actions spawns **256 distinct parallel jobs**, where each job compiles that specific third-party library into a native executable and runs its test suite (`./gradlew test -Pcoordinates=${{ matrix.coordinates }}`).
6. **The Larger Runner Cost Link:** When `-H:Preserve=all` was active in the workflow, each of those **256 jobs** selected `ubuntu-8core-32gb` ($0.032/min) to avoid running out of RAM during whole-program static analysis. 256 separate 8-core 32GB runners running for up to 45 minutes resulted in massive compute expenditure (~$368/run; ~$1,500–$3,600/month).
